# Lindu-EEW Datasets

Every file here falls into one of four provenance classes. `MANIFEST.csv` lists the class, row count and purpose of each file. Files are not split into subfolders because the scripts resolve them by name.

| Class | Meaning | Use it as |
|---|---|---|
| **REAL_DEVICE** | Dumped from the live PostgreSQL/TimescaleDB fed by the ESP32 nodes over MQTT | Primary data acquisition dataset |
| **DERIVED_FROM_REAL** | Computed from REAL_DEVICE files (windows, episodes) | Real-data AI features and episode analysis |
| **EXTERNAL_REAL_CATALOG** | Real events from USGS/BMKG. Local PGA and actuator response are computed, not measured | Context and stress cases |
| **SYNTHETIC** | Generated by scripts (physics model, Omori, GMPE) | Model training and simulation only; never report as measured data |

---

## Methodology and limitations

**Primary dataset.** The data acquisition dataset is the REAL_DEVICE group (section 1): sensor telemetry, node logs, alerts, the heartbeat/PIR log and the actuator log recorded by the prototype nodes into PostgreSQL over MQTT. It satisfies the requirement of a CSV with at least 1,000 timestamped records.

**Why synthetic data is also used.** Real tectonic ground motion of known magnitude cannot be produced on demand, and no damaging earthquake has been recorded by the prototype. Detection and actuator behavior for earthquake-class events is therefore evaluated on generated data, together with manual shake tests on the hardware.

**How the synthetic data is built.**
1. Normal movement was recorded on a live node for about 3 days (baseline noise and everyday motion).
2. Samples of this recording, plus short live tests (for example footstep and high-frequency shocks, and the RMS conversion), were used to set the generator distributions (`pga`, `freq_hz`, `rms`, noise floor). The calibration is described in the commit history (`calibrate dataset distributions against live node tests`).
3. Earthquake-class events are generated from physics models: Omori's law for aftershock timing, a GMPE for attenuation with distance and magnitude, and P-to-S lead time.
4. Actuator columns (`solenoid_*`, latency) in synthetic files are produced by the generator's rule logic. They are not readings from the relays.

**What this means for reporting.**
- Metrics from synthetic files (100% accuracy, latency columns) show that the generated classes are separable and that the rule logic behaves as designed. They are not field performance.
- Field-grounded figures are the real-episode evaluation (section 2) and the hardware trials in the project report (20 trials: alert latency 130.4 ms and solenoid 326.4 ms).
- Synthetic files must be labeled as simulated whenever they are shown or cited.

### 1.3 Actuator log

| File | Rows | Content |
|---|---:|---|
| [`actuator_log.csv`](actuator_log.csv) | 560 | State changes of valve, door, buzzer and LED |

One row is written each time an actuator changes state. The firmware publishes the event over MQTT (`lindu/sensor/<id>/actuator`) and the ingester stores it in the `actuator_log` table. Exported by `export_csv.py` on 2026-10-20.

| Column | Meaning |
|---|---|
| `time` | Time the ingester received the event (UTC) |
| `node_id` | Node that owns the actuator |
| `actuator` | `valve`, `door`, `buzzer` or `led` |
| `state` | New state (see below) |
| `reason` | Cause inferred by the firmware from the alarm state at that moment |

| Actuator | Device (Node B, ESP32 classic) | `state` values |
|---|---|---|
| `valve` | 12V solenoid valve | `OPEN`, `CLOSED` |
| `door` | 12V solenoid door lock | `LOCKED`, `UNLOCKED` |
| `buzzer` | Siren buzzer | `ON`, `OFF` |
| `led` | RGB LED | `NORMAL`, `EARTHQUAKE` |

`reason` values: `MANUAL_OR_RESET` (manual command, alarm cancel, or the state reported at boot), `EARTHQUAKE_ALARM` / `EARTHQUAKE` (earthquake alarm active), `ALARM_OCCUPANCY_PIR` (door unlocked during an alarm because the PIR saw movement in the last 10 minutes), `NORMAL`.

Coverage: the LED logs the alarm mode only, not its colour or blink pattern; the buzzer logs the siren only, not the short haptic ticks. The rows come from functional tests (door and valve cycles, simulated earthquake alarms), not from natural events.

Event taxonomy used by the generators:

| Category | Signature | Consensus | Valve | Door |
|---|---|:---:|:---:|:---:|
| Earthquake (minor to severe) | 0.8 to 6.5 Hz, 10 to 95 s, multiaxial | reached | shut off | unlocked if occupied |
| Foot stomp | 0.12 to 0.35 g, 18 to 36 Hz, under 1.2 s | failed | open | locked |
| Desk shake | 0.15 to 0.45 g, 2 to 7 s, single axis | failed | open | locked |
| Door slam | 0.11 to 0.38 g, 26 to 52 Hz, under 0.5 s | failed | open | locked |
| Dropped object | 0.08 to 0.25 g, 32 to 58 Hz, under 0.3 s | failed | open | locked |
| Passing truck | 0.02 to 0.08 g, 16 to 32 Hz | failed | open | locked |
| Ambient noise | PGA under 0.014 g | none | open | locked |

Model results on these files (held-out 2,000 and 300 samples, both 100%) measure separability of the generated classes, not field performance. Use the real-episode figure in section 2 for reporting.

## 6. Live validation (hardware)

Footstep tests on the live ESP32: heel strikes up to 2.814 g, dominant frequency 18 to 28 Hz, decayed within 0.3 s. With the consensus frequency limit at 8.0 Hz and a 5.0 s buffer, all were rejected: 0 false alarms, valves stayed open.
